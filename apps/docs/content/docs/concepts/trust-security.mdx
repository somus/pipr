---
title: "Trust and security"
description: "How Pipr protects config, secrets, model access, publication, and diagnostic data."
---

Pipr assumes proposed change-request code can be untrusted. Hosted runs take executable policy from the base branch and keep model output behind validation.

## Run-mode boundaries

The source of config, secrets, and publication authority depends on how you run Pipr.

| Boundary | Local review | Provider CI | Trusted webhook worker |
| --- | --- | --- | --- |
| Config | Current workspace | Base commit | Base commit |
| Diff | Local refs or working tree | Exact proposed head and base | Exact proposed head and base |
| Secrets | Local environment or Pi authentication | CI secret store | Worker environment |
| Code-host writes | Disabled | Configured comments and statuses | Configured comments, responses, and statuses |
| Best use | Config and prompt iteration | Trusted CI changes | Forks, commands, replies, and self-hosted delivery |

Use a trusted webhook worker when proposed code can alter the CI job that receives write-capable tokens or model credentials.

## Trusted config

Hosted change-request runs:

1. Load `.pipr/config.ts` and its local imports from the base commit.
2. Validate the plan and required environment variables.
3. Check out the exact proposed head for review.
4. Run the selected tasks.
5. Publish with the base-branch policy.

Changes to `.pipr/config.ts` are reviewed as code, but they do not change the active model, tasks, command permissions, or publication settings for that run.

## Secrets

Reference provider credentials by environment-variable name:

```ts twoslash
// @include: pipr-builder
const model = pipr.model({
  provider: "deepseek",
  model: "deepseek-v4-pro",
  apiKey: pipr.secret({ name: "DEEPSEEK_API_KEY" }),
});
```

Pass the value from the CI or worker secret store. Do not place credentials or private operational notes in config values, prompts, schema metadata, examples, or generated documentation.

## Model workspace

Pi receives read-only tools and a read-only copy of the reviewed workspace. Bounded diff tools can read manifest ranges and base or head snapshots when a reduced manifest needs more context. They do not expose shell or write operations.

Path filters limit changed-code context and publishable findings. They are not a repository-access sandbox, so the model can still inspect related files through allowed read tools.

## Publication controls

Agents do not receive code-host write APIs. Tasks emit output, then Pipr:

- validates inline anchors against the Diff Manifest
- drops invalid or duplicate findings
- applies the configured inline cap
- checks that the change request still points to the reviewed head
- updates Pipr-owned comments and statuses

These controls prevent model output from becoming an unchecked provider-side effect. They cannot guarantee that model judgment is correct, so human review still owns the merge decision.

## Forks and commands

Fork support depends on the provider's secret and CI rules. If a required secret is unavailable, Pipr stops before model execution. The base-config rule still applies to fork-authored changes.

Commands use provider-neutral permission levels:

```text
read < triage < write < maintain < admin
```

Keep commands that expose sensitive context or spend significant provider quota at `write` or higher.

## Diagnostic data

Run bundles can contain repository and model evidence. Treat them as sensitive repository data.

GitHub Actions publishes content-free metadata by default. When `PIPR_RUN_AGE_RECIPIENTS` is configured, it can also publish an encrypted diagnostic package. GitHub access permits discovery and download; a matching local age identity is required to read the diagnostic content.

Trusted webhook stores and opt-in local captures use filesystem access controls. Never store a decryption identity beside its provider artifact or share decrypted diagnostics outside an authorized repository channel.

See [Debug captured runs](/docs/guide/run-observability) for setup and retention behavior.

## Security limits

Pipr cannot prevent false positives, missed defects, or a configured model provider from processing the context you send. Do not run Pipr on code you are not permitted to send to that provider.

Local runs trust the current workspace config and its task code. Run them only on branches whose `.pipr` files you trust.
