Pipr uses the same review pipeline for hosted events, commands, and local runs. The run mode changes where config and diff data come from and whether publication is enabled.

## Run modes

Choose a hosted mode when output must reach the code host. Use local or dry runs to validate behavior without publishing.

| Mode | Starts from | Publishes |
| --- | --- | --- |
| Change request | A supported code-host event | Reviews, inline comments, and checks |
| Command | A matching `@pipr` comment | Review output or a command response |
| Local review | `pipr review --base <ref>` | No |
| Dry run | `pipr dry-run` or `PIPR_DRY_RUN=1` | No |

See [Local runs](/docs/guide/local-runs) for working-tree and ref-to-ref examples.

## Hosted review sequence

A hosted review follows this order:

1. Load `.pipr/config.ts` from the change request's base commit.
2. Validate the selected models, tasks, entrypoints, and required environment variables.
3. Check out the exact proposed head.
4. Build a Diff Manifest from the base and head.
5. Run the selected tasks and agents.
6. Validate the final output against the current diff.
7. Confirm the change request still points to the reviewed head.
8. Publish comments and statuses through the active code host.

Proposed config changes remain visible to review, but they do not alter the policy running against that same change request.

## Diff Manifest

The Diff Manifest is Pipr's changed-code model. It contains changed files, hunks, and ranges that can receive inline comments.

```ts twoslash
// @include: task-context
const manifest = await ctx.change.diffManifest({
  paths: { include: ["src/**"], exclude: ["**/*.generated.ts"] },
});
```

Pass the manifest to `ctx.pi.run(...)` when an agent needs changed-code context:

```ts twoslash
// @include: task-pi-review
const result = await ctx.pi.run(reviewer, { manifest });
await ctx.comment({
  main: result.summary.body,
  inlineFindings: result.inlineFindings,
});
```

Each inline finding must use a path, side, line span, and `rangeId` from the manifest. `paths` limits the manifest and publishable findings, but it does not prevent read-only inspection of related repository files.

For large changes, Pipr can reduce the manifest and attach bounded read tools. Configure provider-call and manifest limits through `pipr.config(...)`; see [Runtime limits](/docs/reference/sdk-reference#runtime-limits) for the exact options.

## Agent execution

Tasks run typed agents through `ctx.pi.run(...)`. Pipr selects the call override first, then the agent model and fallbacks, then the configured default provider.

Agent output must match its declared schema. Invalid output can use the configured repair policy, while transient retries and fallbacks follow the agent settings. Every provider call counts toward `limits.maxAgentRuns` when that limit is set.

## Final output

Each selected task emits one final value:

- `ctx.comment(markdown)` for a main comment
- `ctx.comment({ main, inlineFindings })` for review output
- `ctx.command.reply(markdown)` for a command response

Pipr validates findings, applies inline caps, prevents stale publication, and updates Pipr-owned output on reruns. [Comments and findings](/docs/concepts/comments) covers those behaviors.

## Failure behavior

Pipr stops or narrows output according to what remains safe to publish.

| Failure | Result |
| --- | --- |
| Config or required environment is invalid | The run stops before model execution. |
| Agent output remains invalid | The task fails. |
| One finding has an invalid anchor | Pipr drops that finding and continues. |
| The change request head changed | Pipr stops before publication. |
| A comment or status API fails | The hosted run reports a publication failure. |
| Optional stale-thread cleanup fails | The review remains published and reports the cleanup error. |
