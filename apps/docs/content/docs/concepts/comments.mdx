---
title: "Comments and findings"
description: "How Pipr publishes review comments, validates inline findings, and updates prior results."
---

Review tasks emit structured output. Pipr validates that output and turns it into comments or command responses for the active code host.

## Visible review output

A review can create these surfaces:

| Surface | Location | Purpose |
| --- | --- | --- |
| Main review comment | Change request conversation | Summary, workflow output, and review status |
| Inline review comment | Changed-file diff | One actionable finding on a validated range |
| Command response | Change request conversation | Result for one source `@pipr` command |
| Check or status | Commit or change request | Task or aggregate pass, fail, or neutral result |

Pipr updates its main comment on reruns instead of adding another summary. Hosted change-request reviews can show progress while tasks run and completion details such as models, agent runs, elapsed time, tokens, and reported cost. Use `publication.showHeader`, `showFooter`, `showProgress`, and `showStats` to control those generated sections.

## Emit review output

Publish a main comment:

```ts twoslash
// @include: task-context
await ctx.comment("## Review\n\nNo actionable findings.");
```

Publish a main comment with inline findings:

```ts twoslash
// @include: task-result
await ctx.comment({
  main: result.summary.body,
  inlineFindings: result.inlineFindings,
});
```

A task must emit exactly one final output. Use `ctx.command.reply(...)` instead when a command should answer its source comment without replacing the main review.

## Inline findings

Each finding targets one commentable Diff Manifest range:

```ts
const finding = {
  body: "This retry path can submit the request twice.",
  path: "src/retry.ts",
  rangeId: "src/retry.ts:RIGHT:42-45",
  side: "RIGHT",
  startLine: 42,
  endLine: 45,
  suggestedFix: "return await retryOnce(request);",
};
```

`suggestedFix` must contain exact replacement code for the selected range. GitHub and GitLab render native suggestions; other supported hosts show fenced replacement code.

## Dropped findings

Pipr drops a finding when it cannot publish it at a verified location. The remaining valid findings still publish.

| Reason | Fix |
| --- | --- |
| The path is not in the manifest | Ask the agent to review only manifest files. |
| The `rangeId` or line span does not identify a valid range | Use the exact anchor from the manifest. |
| The finding is outside a configured path scope | Pass the same `paths` to manifest construction and agent execution. |
| The finding duplicates another current finding | Keep one finding per issue and range. |
| The output contains unsupported fields | Use a built-in schema or map a custom schema to `ReviewFinding[]`. |

Hosted and local structured results expose dropped findings for diagnosis. See [Troubleshooting](/docs/guide/troubleshooting#findings-are-dropped) when comments are missing.

## Inline caps

`publication.maxInlineComments` limits how many valid findings reach the diff. Keep the main comment useful when the cap hides lower-priority findings.

```ts twoslash
// @include: pipr-builder
pipr.config({
  publication: { maxInlineComments: 5 },
});
```

## Reruns and prior findings

Pipr stores bounded state in its own comments so later runs can update the main comment, avoid duplicate inline comments, and recheck prior findings. `publication.maxStoredFindings` controls how many finding records remain available to later runs.

Custom tasks can read prior state:

```ts twoslash
// @include: task-context
const prior = await ctx.review.prior();
```

When supported, Pipr can recheck its inline findings after new commits or authorized replies. A fixed finding can receive a reply and native thread resolution; a still-valid finding can receive a short explanation. Set `publication.autoResolve` to `false` to disable this behavior.

## Command responses

Command responses are keyed to the source comment and update in place as the command moves from accepted to running and then to its final result.

```ts twoslash
// @include: task-context
await ctx.command?.reply("The failing test is `retry.test.ts`.");
```

Use [Entrypoints](/docs/guide/entrypoints) for command grammar and permissions.
