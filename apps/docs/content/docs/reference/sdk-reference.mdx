The Pipr SDK is the public TypeScript authoring API for `.pipr/config.ts`.

```ts
import { definePipr } from "@usepipr/sdk";
```

Type and schema names are exported from the SDK root:

```ts
import type { AgentTool, ReviewFinding, ReviewResult, ToolRunOptions } from "@usepipr/sdk";
```

## Concept map

The SDK maps directly to Pipr's runtime primitives. Use this table to choose the API surface before reading individual type details.

| Primitive | SDK surface |
| --- | --- |
| Trigger | `pipr.task({ on })`, `pipr.review({ on })`, `defaultReviewTriggers`, `pipr.command(...)` |
| Review Task | `pipr.task(...)`, `TaskContext` |
| Diff Manifest | `ctx.change.diff(...)`, `DiffContext`, `DiffManifest`, `ReviewFinding.rangeId` |
| Agent | `pipr.agent(...)`, `ctx.pi.run(...)`, `ctx.pi.all(...)` |
| Findings | `pipr.finding(...)`, `ctx.review.select(...)`, `ctx.check.gate(...)` |
| Review Output | `md`, `ctx.comment(...)`, `ctx.command?.reply(...)`, `CommentValue` |
| Publication | `pipr.config({ publication })`, Pipr runtime validation and code host adapters |

For the narrative model, see [How Pipr works](/docs/concepts).

## `definePipr`

Every config must default-export a synchronous factory:

```ts
import { definePipr } from "@usepipr/sdk";

export default definePipr((pipr) => {
  // register models, agents, tasks, commands, limits, tools
});
```

The callback must be synchronous. Runtime work belongs in `pipr.task(...)`, not at config load time.

## Models and secrets

Model ids default to `<provider>/<model>`:

```ts
const model = pipr.model("deepseek/deepseek-v4-pro", { thinking: "high" });
```

<auto-type-table path="packages/sdk/src/index.ts" name="ModelOptions" />

Pipr passes provider and model IDs to Pi. [Browse Pi's Model Catalog](https://pi.dev/models) for current identifiers, providers, context limits, and pricing. Use `id` only when you configure the same provider and model with different API keys or thinking levels. `pipr.secret({ name })` stores only the environment variable name. It does not read or serialize the secret during plan creation.

Omit `apiKey` to read the provider's standard environment variable, such as `DEEPSEEK_API_KEY` for `deepseek/...`. Pass `apiKey: pipr.secret({ name })` to read a different variable. Config loading fails when you omit `apiKey` for a provider without a standard API-key variable. Pass `apiKey: "local"` only for a model that local runs select through local Pi login credentials. Hosted runs don't receive your Pi agent directory, so hosted model selections must not use `"local"`.

## Review preset

`pipr.review(...)` is a preset over the same helpers custom tasks use. It runs one findings agent over `ctx.change.diff()`, selects findings with `ctx.review.select(...)`, optionally runs a summary agent, optionally applies `ctx.check.gate(...)`, and publishes with `ctx.comment(...)`.

```ts
pipr.config({ publication: { maxInlineComments: 5 } });

pipr.review({
  id: "review",
  model,
  instructions: "Review the change for actionable correctness and security defects.",
  summary: { instructions: "Summarize changed behavior, risk, and reviewer focus." },
  tools: pipr.tools.readOnly,
  timeout: "10m",
  paths: {
    include: ["packages/runtime/**"],
    exclude: ["**/*.test.ts"],
  },
});
```

Omit `summary` to run only the findings agent. Pass `summary: { agent }` to use your own summary agent; it receives `ReviewSummaryInput` with a bounded `diff` summary, the change request, and the selected `findings`.

### Triggers

`on` defaults to `defaultReviewTriggers`: change request `opened`, `updated`, `reopened`, and `ready`, plus `@pipr review` with write permission.

```ts twoslash
import { defaultReviewActions, defaultReviewTriggers } from "@usepipr/sdk";
import type { ChangeRequestAction } from "@usepipr/sdk";

const actions: readonly ChangeRequestAction[] = defaultReviewActions;
actions;
// ^?

defaultReviewTriggers;
// ^?
```

Command `permission` is provider-neutral:

```text
read < triage < write < maintain < admin
```

Adapters map native roles into this order. To run the review only from a command:

```ts
pipr.review({
  id: "review",
  model,
  instructions: "Review for actionable defects.",
  on: { command: { pattern: "@pipr review", permission: "write" } },
});
```

### Custom findings

Declare extra finding fields with `pipr.finding(...)`. Enum fields become facets: they rank findings in declaration order (first value is highest) and label outcome analytics. Pipr does not hardcode severity or category; declare only what your review needs.

```ts
const finding = pipr.finding({
  title: z.string().max(160),
  severity: z.enum(["critical", "high", "medium", "low"]),
  category: z.enum(["correctness", "security", "test-coverage"]),
});

pipr.review({
  id: "review",
  model,
  finding,
  instructions: "Assign severity by merge impact.",
  gate: { failOn: { severity: ["critical", "high"] } },
  render: ({ findings }) => ({
    main: md`## Review\n\n${findings.length} findings.`,
    inlineFindings: findings.map((item) => ({
      ...item,
      body: String(md`**${md.label(item.severity)}:** ${item.title}\n\n${item.body}`),
    })),
  }),
});
```

`paths` scopes the Diff Manifest and publishable Inline Review Comments for that review. It is not a filesystem sandbox: Pi read-only tools can still inspect the repository, and Pipr prompts the agent to read nonmatching files only when needed to review matching files.

The built-in findings and summary prompts are fixed so the runtime can supply the scoped Diff Manifest and selected findings consistently. Use `pipr.agent(...)` and `pipr.task(...)` when you need a custom per-run `prompt`. Do not repeat the change number, title, description, JSON output contract, or generic `suggestedFix` rules in instructions. Core supplies those sections once.

## Agents

Use `pipr.agent(...)` for non-default structured agent calls:

Agents have two prompt layers. Use `instructions` for stable behavior that applies to every run of the agent, such as role, review focus, and output constraints. Use `prompt` for the concrete task for one invocation. The `prompt` function receives the typed input passed to `ctx.pi.run(...)` and the agent prompt context, then Pipr renders it after the agent instructions in the Pi prompt.

```ts
const security = pipr.agent({
  name: "security-reviewer",
  model,
  instructions: "Review only security issues.",
  output: pipr.schemas.review,
  prompt: () => pipr.prompt`
    Review this change request for exploitable security issues.
  `,
  timeout: "10m",
});
```

Pipr always validates structured output and allows one repair attempt for invalid output; the repair is a follow-up turn in the same conversation. Transient provider failures retry inside the agent harness with backoff, so agents have no retry setting.

`agent.extend(...)` creates a derived agent and appends additional instructions to the base instructions:

```ts
const strictSecurity = security.extend({
  instructions: "Ignore style-only findings.",
});
```

## Multi-agent orchestration

Use one task when multiple agents should produce one published review. Pass the `ctx.change.diff()` value to agents that need changed-code context; Pipr detects it in the input and supplies the Diff Manifest prompt and helper tools. Run independent agents with `ctx.pi.all(...)`, which checks the agent-run budget for every request before starting any of them.

```ts
const base = pipr.agent({
  name: "base-specialist",
  model,
  instructions: "Return only actionable findings with valid ranges.",
  output: pipr.schemas.review,
  prompt: (input: { diff: DiffContext; focus: string }) => pipr.prompt`
    ${pipr.section("Focus", input.focus)}
  `,
});

const security = base.extend({
  name: "security-specialist",
  instructions: "Focus on exploitable security issues.",
});
const tests = base.extend({
  name: "test-specialist",
  instructions: "Focus on missing regression tests.",
});

const aggregator = pipr.agent({
  name: "review-aggregator",
  model,
  instructions: "Summarize the validated specialist findings without inventing defects.",
  output: pipr.schemas.summary,
  tools: pipr.tools.readOnly,
  prompt: (input: { findings: unknown; prior: PriorReview }) => pipr.prompt`
    ${pipr.section("Prior review", pipr.json(input.prior, { maxCharacters: 20000 }))}
    ${pipr.section("Validated specialist findings", pipr.json(input.findings))}
  `,
});

pipr.task({
  name: "multi-agent-review",
  on: { changeRequest: true },
  async run(ctx) {
    const diff = await ctx.change.diff({ compressed: true });
    const prior = await ctx.review.prior();
    const [securityResult, testResult] = await ctx.pi.all([
      { agent: security, input: { diff, focus: "security" } },
      { agent: tests, input: { diff, focus: "tests" } },
    ]);
    const { findings } = ctx.review.select([
      securityResult.inlineFindings,
      testResult.inlineFindings,
    ]);
    const summary = await ctx.pi.run(aggregator, { findings, prior });
    await ctx.comment({ main: summary.body, inlineFindings: findings });
  },
});
```

## Tasks

Tasks are the executable review units. They receive a `TaskContext` and optional parsed input. `on` declares the events that start the task:

```ts
pipr.task({
  name: "security-review",
  on: {
    changeRequest: ["opened", "updated"],
    command: { pattern: "@pipr security", permission: "write" },
  },
  check: { name: "security" },
  async run(ctx) {
    const paths = { include: ["packages/runtime/**"] };
    const diff = await ctx.change.diff({ compressed: true, paths });
    const result = await ctx.pi.run(security, { diff }, { paths });
    const { findings } = ctx.review.select(result.inlineFindings);

    await ctx.comment({ main: result.summary.body, inlineFindings: findings });
  },
});
```

`on.changeRequest: true` uses `defaultReviewActions`. Change request triggers are only available for tasks without input. Command tasks with input declare `parse`:

```ts
pipr.task<{ question: string }>({
  name: "ask",
  on: {
    command: {
      pattern: "@pipr ask <question...>",
      permission: "read",
      parse: (args) => ({ question: args.question ?? "" }),
    },
  },
  async run(ctx, input) {
    await ctx.command?.reply(md`You asked: ${input.question}`);
  },
});
```

Use `pipr.command({ pattern, task })` only to add another command to a task handle you already registered.

Local review runs tasks with a change request trigger. Set `local: false` on a task when it should be skipped by `pipr review` but still run in CI:

```ts
pipr.task({
  name: "ci-only",
  on: { changeRequest: true },
  local: false,
  async run(ctx) {
    const diff = await ctx.change.diff({ compressed: true });
    const result = await ctx.pi.run(security, { diff });
    await ctx.comment({ main: result.summary.body, inlineFindings: result.inlineFindings });
  },
});
```

Use `ctx.run.trigger === "local"` inside a task when the task should run in both environments but render different output. Keep `local: false` for tasks that should not run locally at all.

## Task context

Task handlers use this context to read change data, run Pi, publish results, and report status.

| Property | Purpose |
| --- | --- |
| `ctx.run.id` | Stable id for the selected review run. |
| `ctx.run.trigger` | Task trigger: `change-request`, `command`, or `local`. |
| `ctx.platform.id` | Active code host adapter id. Don't use it to infer the Review Run trigger. |
| `ctx.repository` | Provider-neutral repository metadata. |
| `ctx.change` | Provider-neutral change request metadata plus diff helpers. |
| `ctx.change.diff(options?)` | Build the branded Diff Manifest context passed to agents. |
| `ctx.pi.run(agent, input, options?)` | Execute a Pi-backed agent and validate structured output. |
| `ctx.pi.all(requests)` | Run independent agent requests concurrently after one budget check. |
| `ctx.command` | Present only for command-triggered tasks. Includes `name`, `line`, parsed `arguments`, and `reply(markdown)`. |
| `ctx.review.prior()` | Read prior review state: `main?`, `reviewedHeadSha?`, and `inlineFindings[]` with `id`, `status`, `path`, `rangeId`, `side`, `startLine`, and `endLine`. |
| `ctx.review.select(findings, options?)` | Validate, deduplicate, rank, and cap findings. Returns kept `findings` and `dropped` findings with reasons. |
| `ctx.review.validateFindings(findings, options?)` | Validate and deduplicate findings without ranking or capping. Extra finding metadata is preserved. |
| `ctx.check.gate(findings, options)` | Derive the task check from blocking findings. |
| `ctx.check.pass/fail/neutral(summary?)` | Set one explicit task check result. Check failure does not fail the Action process by itself. |
| `ctx.comment(value)` | Emit the selected run's final Main Review Comment markdown and Inline Review Comments. |
| `ctx.log` | Write runtime logs. |

`ctx.change.diff(...)` returns a `DiffContext`. Its `manifest` holds commentable file ranges, and findings must reference those ranges by `rangeId`. `summary()` returns a bounded file-level projection for summary agents. Pipr only treats the branded value as changed-code context; an agent input may contain at most one.

When structural analysis is available, manifest files and ranges can include best-effort `changedSymbols` and declaration summaries. Review logic must not require those optional fields.

`ctx.command.reply(...)` emits a normal change-request comment response for command tasks. A task must emit exactly one final output: either `ctx.comment(...)` for review publication or `ctx.command.reply(...)` for command response publication.

When a custom task uses path scoping, pass the same `paths` to `ctx.change.diff(...)` and `ctx.pi.run(...)`. Pipr infers that scope when `ctx.review.select(...)` receives the exact finding arrays returned by `ctx.pi.run(...)`. Pass `{ paths }` after mapping, sorting, or combining arrays.

`ctx.review.select(...)` ranks findings first, so when two findings share a fingerprint the higher-ranked one is kept. It then caps at `limit`, which defaults to `publication.maxInlineComments`, and reports capped findings with reason `cap`. Pass `limit: list.length` before `ctx.check.gate(...)` so the cap cannot hide blockers. Pass `requireSuggestedFix: true` to keep only findings whose `suggestedFix` Pipr can publish as an exact suggestion.

Call `ctx.review.select(...)` before findings affect a required check, table, or second-stage agent. Final publication validation still runs in `ctx.comment(...)`.

```ts
const { findings: risks } = ctx.review.select(result.risks, { finding: risk, limit: result.risks.length });
const gate = ctx.check.gate(risks, { failOn: { severity: ["critical", "high"] } });
```

## Code-host statuses

Task-level `check` controls individual code-host statuses and aggregate participation:

```ts
const task = pipr.task({
  name: "security",
  check: { enabled: true, name: "security", required: true },
  async run(ctx) {
    ctx.check.pass("Security review completed.");
    await ctx.comment("## Security review\n\nNo blocking findings.");
  },
});
```

When `check` is an object, the individual task status is enabled by default. `required` defaults to `true`. Use `check: false` to opt a task out of both its individual status and the aggregate status. A task without `check` does not get an individual status, but still participates in the aggregate when aggregate statuses are enabled.

Enable the aggregate status only when you want one Pipr-owned result across multiple tasks:

```ts
pipr.config({
  checks: { aggregate: { enabled: true, name: "all" } },
});
```

Statuses publish for supported change-request events when the selected adapter exposes status publication. GitHub uses Check Runs, GitLab uses external commit statuses, Azure DevOps uses pull request statuses, and Bitbucket plus Gitea-compatible hosts use source-commit statuses. They do not publish for command responses, local runs, or dry runs. `ctx.check.pass/fail/neutral(...)` can be called at most once per task. A failed task status does not fail the delivery process by itself.

## Global config

`pipr.config(...)` sets global runtime behavior:

```ts
pipr.config({
  publication: {
    maxInlineComments: 5,
    maxStoredFindings: 50,
    showHeader: true,
    showFooter: true,
    showStats: true,
    showProgress: true,
    autoResolve: {
      model,
      instructions: "Respect maintainer explanations about deliberate product behavior.",
      synchronize: true,
      userReplies: {
        enabled: true,
        respondWhenStillValid: true,
        allowedActors: "author-or-write",
      },
    },
  },
  checks: {
    aggregate: { enabled: true },
  },
  limits: {
    timeoutSeconds: 300,
  },
});
```

`maxInlineComments` caps inline publication. `maxStoredFindings` defaults to `50`, accepts `0` through `100`, and limits prior findings available to later runs. Setting it to `0` disables finding-based cross-run behavior after the current run.

`showHeader`, `showFooter`, `showStats`, and `showProgress` independently control the generated title, attribution, completion details, and hosted-run progress. All four default to `true`.

`publication.autoResolve` defaults to enabled. Use `autoResolve: false` to disable thread cleanup and user-reply handling. If `model` is omitted, Pipr uses the default provider. Native thread cleanup still depends on code-host support and credentials.

`userReplies.allowedActors` controls who can trigger verifier replies:

| Value | Behavior |
| --- | --- |
| `"author-or-write"` | PR author or users with write access. Default. |
| `"write"` | Only users with write access. |
| `"any"` | Any commenter. Use only when public reply-triggered model calls are acceptable. |

`"author-or-write"` lets the PR author trigger verifier model calls from review-comment replies, including external contributors on public forks. Use `"write"` when only trusted repository collaborators should spend provider quota or send bounded diff, finding, and thread context to the configured model provider.

Set `respondWhenStillValid: false` to keep user-reply verifier runs silent unless the finding is resolved.

## Comment output

Each selected run must emit exactly one final output. Use `ctx.comment(value)` for review publication, or `ctx.command.reply(value)` for command response publication. Missing or duplicate final outputs fail the run.

Use `ctx.comment(...)` for Main Review Comment markdown. Build Markdown with `md`: interpolated values are escaped so model-authored text cannot inject raw HTML or hidden Pipr markers, while values produced by `md` are inserted as-is.

```ts
await ctx.comment(md.blocks(md`## Security review`, result.summary.body, md.list(notes)));
```

| Helper | Output |
| --- | --- |
| ``md`...` `` | Markdown with escaped interpolations. The template is dedented; interpolated text keeps its own whitespace. |
| `md.raw(value)` | Trusted Markdown, inserted without escaping. |
| `md.line(value)` | One escaped line. |
| `md.label(value)` | `test-coverage` as `Test coverage`. |
| `md.list(items, { ordered? })` | Bullet or numbered list; empty input renders nothing. |
| `md.table(rows, columns)` | Table with escaped single-line cells. |
| `md.details(summary, body)` | Collapsed `<details>` block; empty body renders nothing. |
| `md.callout({ icon, title, body })` | One-line blockquote callout. |
| `md.blocks(...blocks)` | Blocks joined by blank lines, skipping empty blocks. |

Inline finding `body` values are strings; wrap `md` output with `String(...)`.

Use object form to publish a Main Review Comment, Inline Review Comments, or both:

```ts
await ctx.comment({
  main: "## Security review\n\nFound one issue.",
  inlineFindings: [{
    body: "This branch can throw before cleanup runs.",
    path: "src/server.ts",
    rangeId: "rng_...",
    side: "RIGHT",
    startLine: 42,
    endLine: 42,
  }],
});
```

For findings-only output, omit `main`:

```ts
await ctx.comment({ inlineFindings });
```

Structured output must contain `main`, `inlineFindings`, or both. `{ inlineFindings: [] }` is valid; `{}` is rejected.

Pipr validates findings against the Diff Manifest, drops invalid findings, dedupes finding markers, and caps inline publication. Use `ctx.review.select(...)` earlier when task code consumes findings before this final boundary.
Subjective labels such as severity, confidence, or category are not part of the built-in finding contract. Declare them with `pipr.finding(...)` and render them into your own `ctx.comment(...)` markdown when your workflow needs them.

## Tools

`pipr.tool(...)` defines typed model-facing tools. Names use 1-64 letters, digits, underscores, or hyphens, and descriptions are at most 4096 characters; other values fail when the config loads.

```ts
const lookupOwner = pipr.tool({
  name: "lookup_owner",
  description: "Return the owner for a repository path.",
  input: myInputSchema,
  output: myOutputSchema,
  async run({ input, ctx, signal }) {
    signal?.throwIfAborted();
    return await lookupOwnerFromCatalog(input.path, ctx);
  },
  toModelOutput(output) {
    return {
      owner: output.team,
    };
  },
});
```

Tool `run(...)` receives:

| Field | Meaning |
| --- | --- |
| `input` | Parsed tool input. |
| `ctx` | Runtime-provided tool context. |
| `signal` | Optional abort signal. |

Use `run({ input, ctx, signal })` for custom tools. Pipr rejects legacy
`execute(context, input)` tool definitions with `Tool '<name>' must define run`.

`toModelOutput(...)` can project a rich tool result into a smaller model-facing value.

## Schemas

Built-in schemas:

| Schema | Use |
| --- | --- |
| `pipr.schemas.review` | Main review result with summary and inline findings. |
| `pipr.schemas.inlineFindings` | Inline findings without a summary. |
| `pipr.schemas.summary` | Main-comment summary block. |

Custom schemas are useful for intermediate agents and workflows that map their final output into Pipr publication calls:

```ts
import { definePipr, z } from "@usepipr/sdk";

export default definePipr((pipr) => {
  const specialistOutput = pipr.schema({
    id: "security/specialist-output",
    schema: z.strictObject({
      summary: z.string(),
      risks: z.array(z.string()),
    }),
  });

  const summaryOutput = pipr.jsonSchema<{ summary: string }>({
    id: "security/summary",
    schema: {
      type: "object",
      additionalProperties: false,
      required: ["summary"],
      properties: {
        summary: { type: "string" },
      },
    },
  });

  void specialistOutput;
  void summaryOutput;
});
```

Use `pipr.schemas.review` when an agent directly returns publishable Inline Review Comments. `suggestedFix` is optional exact replacement code for the selected range. GitHub and GitLab render it as a native suggestion; Azure DevOps, Bitbucket, Gitea, Forgejo, and Codeberg render fenced replacement code.

Custom output receives review guidance when a reachable `properties` or `items` path contains one object that directly declares `body`, `path`, `rangeId`, `side`, `startLine`, and `endLine`. Pipr follows local `$ref` links used by generated first-party schemas, but it does not infer findings by merging fields across conditional, alternative, pattern, or tuple schemas.

Automatic large-diff splitting requires a closed root object whose only declared and required property is `inlineFindings`, with that property defined as an array of the supported finding object. Pipr honors the array's integer `maxItems`; custom output with any other root shape runs once.

The `z` export is the recommended typed path for JSON-Schema-representable schemas. Generated `.pipr/types` include a standalone Zod authoring subset so `pipr init` projects type-check without installing `zod`; use `pipr.jsonSchema<T>()` for advanced JSON Schema shapes or when a Zod helper is outside that generated subset.

Parsing helpers and public Zod schemas are exported from `@usepipr/sdk`:

```ts
import {
  parseReviewFinding,
  parseReviewResult,
  reviewFindingSchema,
  reviewResultSchema,
  reviewSchemaExample,
  reviewSummarySchema,
} from "@usepipr/sdk";
```

Use `reviewResultSchema`, `reviewFindingSchema`, and `reviewSummarySchema` when you need the public review contract as Zod values.

## Prompts

Use prompt helpers to keep prompts structured:

```ts
pipr.prompt`
  ${pipr.section("Review policy", "Only report actionable defects.")}
`;
```

`pipr.json(value, { pretty, maxCharacters })` renders bounded JSON and throws if the value is not fully JSON-serializable or exceeds `maxCharacters`.

## Runtime limits

Set global execution limits through `pipr.config(...)`.

```ts
pipr.config({
  limits: {
    timeoutSeconds: 300,
    maxAgentRuns: 16,
    diffManifest: {
      maxShards: 4,
      fullMaxBytes: 131072,
      fullMaxEstimatedTokens: 32000,
      condensedMaxBytes: 262144,
      condensedMaxEstimatedTokens: 64000,
      toolResponseMaxBytes: 65536,
    },
  },
});
```

These limits control runtime timeout, provider-call count, and Diff Manifest prompt sizing.

| Field | Values and default | Behavior |
| --- | --- | --- |
| `limits.diffManifest.maxShards` | Positive integer; defaults to `4` | Caps automatic fan-out from one review invocation. Set it to `1` to disable splitting. |
| `limits.maxAgentRuns` | Positive integer; unlimited when omitted | Caps total provider invocations across all tasks and agents in one Review Run. |

`ctx.pi.run(agent, input, { maxShards })` overrides `limits.diffManifest.maxShards` for that invocation. Omit it to inherit the global value; set it to `1` to disable splitting for only that call.

Each shard, output repair, and fallback consumes one agent run. Transient provider retries inside the agent harness do not. Increase `maxShards` only when a reduced unit still exceeds the provider context limit.

## Results and run bundles

The SDK exports parsers and schemas for stable machine-readable results:

| Surface | Types | Parsers and schemas |
| --- | --- | --- |
| CLI and Action result | `PiprResult`, `PiprRunSummary` | `parsePiprResult`, `piprResultSchema` |
| Review output | `ReviewResult`, `ReviewFinding`, `ReviewSummary` | `parseReviewResult`, `parseReviewFinding`, review schemas |
| Captured run data | `RunBundle`, `RunBundleManifest`, `RunBundleEnvelope` | `parseRunBundle`, `parseRunBundleManifest`, `parseRunBundleEnvelope` |

Use the parser before reading an external JSON value:

```ts
import { parsePiprResult } from "@usepipr/sdk";

const result = parsePiprResult(JSON.parse(serializedResult));
```

CLI and Action results include `formatVersion`; reject unsupported versions before consuming kind-specific fields. Run bundles can contain sensitive repository evidence, so follow [run-bundle security guidance](/docs/concepts/trust-security#diagnostic-data).

`PiprRunSummary` version 2 can report `cacheReadTokens`, `cacheWriteTokens`, and a separate `cacheUsageStatus`. `diffContextCoverage` reports covered and total file and range counts for the current workflow only. These fields are optional when parsing stored version 2 results; Pipr emits cache status for current agent runs and omits coverage when no Diff Manifest was supplied.

## Plugins

Plugins install config-time handles through the builder:

```ts
import { definePlugin, z } from "@usepipr/sdk";

const owners = definePlugin((pipr) => {
  const input = pipr.schema({
    id: "owners/input",
    schema: z.strictObject({ path: z.string() }),
  });
  const output = pipr.schema({
    id: "owners/output",
    schema: z.strictObject({
      path: z.string(),
      owner: z.string(),
      policy: z.string(),
    }),
  });

  return {
    tool: pipr.tool({
      name: "owner_lookup",
      description: "Look up path owners.",
      input,
      output,
      run({ input }) {
        if (input.path.startsWith("packages/runtime/")) {
          return {
            path: input.path,
            owner: "runtime",
            policy: "Review publication behavior strictly.",
          };
        }
        return {
          path: input.path,
          owner: "general",
          policy: "Use the default repository policy.",
        };
      },
      toModelOutput(result) {
        return { path: result.path, owner: result.owner, policy: result.policy };
      },
    }),
  };
});

const ownerTools = pipr.use(owners);

const reviewer = pipr.agent({
  name: "owner-aware-review",
  model,
  output: pipr.schemas.review,
  tools: [...pipr.tools.readOnly, ownerTools.tool],
  instructions: "Use owner_lookup when ownership policy is relevant to the review.",
  prompt: () => "Review this change request.",
});

pipr.task({
  name: "owner-aware-review",
  on: { changeRequest: ["opened", "updated"] },
  async run(ctx) {
    const diff = await ctx.change.diff({ compressed: true });
    const review = await ctx.pi.run(reviewer, { diff });
    await ctx.comment({
      main: review.summary.body,
      inlineFindings: review.inlineFindings,
    });
  },
});
```

Plugin setup runs during config loading. Runtime effects still belong in tasks and tools. Task, agent, and tool values are opaque handles; expose a separate plugin operation when task code needs callable behavior.
