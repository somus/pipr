title: "GitLab"
description: "Run Pipr reviews and commands on GitLab.com or GitLab Self-Managed."

Use GitLab CI for trusted automatic merge-request reviews. Use a dedicated webhook worker for commands, reply verification, forks, or repositories where proposed changes can alter the pipeline.

## Configure GitLab CI

Generate `.gitlab-ci.yml` with the repository config:

```bash
pipr init --adapters gitlab
```

The generated job runs only for merge-request pipelines and fetches full history:

```yaml
pipr:
  image:
    name: ghcr.io/somus/pipr:v0.6.3 # x-release-please-version
    entrypoint: [""]
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  variables:
    GIT_DEPTH: "0"
    PIPR_CODE_HOST: "gitlab"
  script:
    - pipr host-run --host gitlab --config-dir .pipr
```

Configure masked CI/CD variables:

| Variable | Purpose |
| --- | --- |
| `GITLAB_TOKEN` | Read the merge request and publish notes, discussions, and statuses |
| Model-provider key | Match the secret name in `.pipr/config.ts` |

Give the GitLab project token API scope and a role that can read code, comment on merge requests, resolve discussions, and create commit statuses.

For GitLab Self-Managed, Pipr uses the predefined `CI_API_V4_URL` and `CI_SERVER_URL`. Pass `--runtime-image <internal-image>` to `pipr init` when runners cannot pull from GHCR.

GitLab CI comes from source control. Do not expose write-capable or model credentials when untrusted merge-request code can replace the executed job.

## Configure a trusted webhook worker

Run one worker for one dedicated checkout:

```bash
export GITLAB_TOKEN="..."
export GITLAB_API_URL="$GITLAB_INSTANCE_API_URL"
export PIPR_WEBHOOK_SECRET="..."
export DEEPSEEK_API_KEY="..."

pipr webhook serve \
  --host gitlab \
  --repository group/project \
  --workspace /srv/pipr/project \
  --database /var/lib/pipr/webhooks.sqlite \
  --hostname 127.0.0.1 \
  --port 8787
```

Omit `GITLAB_API_URL` for GitLab.com. For Self-Managed, set the complete REST v4 root, including any installation path prefix.

Create a project webhook with the same secret, then enable:

- Merge request events
- Comments

Place the loopback listener behind an HTTPS reverse proxy and persist the SQLite directory. Use [Deploy the webhook runner with Docker](/docs/guide/webhook-docker) for a complete deployment.

## Supported behavior

GitLab supports:

- merge-request open, update, reopen, merge, and close events
- trusted base config and exact-head checkout
- main comments and single-line or multiline inline discussions
- native suggestion blocks
- `@pipr` commands with member permission checks
- verifier replies and discussion resolution
- task and aggregate commit statuses
- stale-head rejection before publication
