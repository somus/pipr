---
title: "Troubleshooting"
description: "Diagnose Pipr config, model, delivery, and publication failures."
---

Start with the narrowest command that reproduces the failure. Fix config locally before debugging provider delivery.

## Choose the first diagnostic

| Symptom | Start with |
| --- | --- |
| Config does not load | `pipr check` |
| The resolved plan is wrong | `pipr inspect` |
| Local review cannot find a base | `pipr review --base <ref>` |
| A hosted run does not publish | `pipr runs show --pr <number>` |
| A command is ignored | Check event, pattern, arguments, and permission |
| Inline findings are missing | Inspect `droppedFindings` |
| Model output is invalid | Inspect the run's repair count |
| A small change runs slowly | Inspect the run timeline |
| Publication stopped after a push | Compare the reviewed and current head |

For a first setup, check config, resolved plan, model secret, delivery configuration, provider permissions, untrusted-change boundaries, stale head, and dropped findings in that order.

## Config does not load

Run:

```bash
pipr check
```

Common causes include:

- `.pipr/config.ts` does not default-export `definePipr(...)`
- the config callback is asynchronous
- a local import cannot resolve
- a task, command, or model ID is duplicated
- a command pattern does not start with `@pipr`
- a secret name is not a valid environment-variable name

After the check passes, run `pipr inspect` to confirm the selected models, tasks, commands, tools, publication settings, and limits.

## A provider secret is missing

Match the name passed to `pipr.secret(...)` with the variable exposed by local execution, CI, or the webhook worker.

For GitHub:

```yaml
env:
  DEEPSEEK_API_KEY: ${{ secrets.DEEPSEEK_API_KEY }}
```

Use `pipr check --require-env` when local validation must fail on missing model variables.

## Local review cannot find a base

Fetch the comparison branch and pass it explicitly:

```bash
git fetch origin main
pipr review --base origin/main
```

Use `--head` only for a committed ref other than the working tree.

## GitHub Action does not publish

Run `pipr runs show --pr <number>` first. Then confirm:

- `actions/checkout` uses `fetch-depth: 0`
- `GITHUB_TOKEN` reaches the Action
- workflow permissions cover enabled comment and check features
- the pull request action matches a configured entrypoint
- a command comment targets a pull request rather than a plain issue
- `PIPR_DRY_RUN` is not enabled

See [GitHub Action permissions](/docs/guide/github-action#permissions) for the required permission map.

## Command comment is ignored

Confirm that the comment:

- was newly created on a change request
- starts with the configured `@pipr` pattern
- supplies every required argument
- comes from an actor with the configured permission
- maps to a registered command

Edited comments do not trigger command parsing. See [Entrypoints](/docs/guide/entrypoints#commands).

## Findings are dropped

Pipr drops invalid findings and continues with valid ones. Read `droppedFindings` from the structured result.

Common causes include:

- the path is not in the Diff Manifest
- the `rangeId`, side, or lines do not match a valid range
- the finding falls outside configured path scope
- the file is binary, removed, generated, locked, or too large for inline review
- another current finding duplicates the same issue and range

Pass the manifest to the agent and map custom output to exact manifest anchors. See [Comments and findings](/docs/concepts/comments#dropped-findings).

## Model output is invalid

Agent output must match the declared schema after the configured repair policy.

If invalid output persists:

- shorten and clarify the instructions
- use SDK schema helpers instead of restating JSON syntax
- remove prose requested outside the structured result
- simplify custom schema nesting
- reproduce with the smallest local diff

## Publication reports a stale head

Pipr stops before writing when the change request head no longer matches the reviewed commit. Rerun on the latest commit.

## A verifier cannot resolve a thread

Verifier replies and native resolution require provider support and sufficient credentials. On GitHub, `${{ github.token }}` may publish the reply while GitHub reports `viewerCanResolve: false`.

If native resolution is required, pass a user credential with pull request write access as `GITHUB_TOKEN`. See [GitHub Action permissions](/docs/guide/github-action#permissions).
