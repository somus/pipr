---
title: "Azure DevOps"
description: "Run Pipr reviews and commands on Azure DevOps Services or Server."
---

Pipr supports Azure DevOps Services plus Azure DevOps Server 2022 and 2022.1. Use a trusted service-hook worker by default. Use a branch-policy pipeline only when pull request authors cannot change the executed pipeline definition.

## Generate the adapter files

Run:

```bash
pipr init --adapters azure-devops
```

This creates `azure-devops.pipr.env.example` and `azure-pipelines.pipr.yml`. Copy variable names into the trusted secret store and keep checked-in example values empty.

Configure:

| Variable | Purpose |
| --- | --- |
| `AZURE_DEVOPS_ORGANIZATION` | Azure DevOps Services organization |
| `AZURE_DEVOPS_COLLECTION_URL` | Server collection root; omit the organization when set |
| `AZURE_DEVOPS_API_VERSION` | `7.1` for Services and Server 2022.1; `7.0` for Server 2022 |
| `AZURE_DEVOPS_BEARER_TOKEN` or `AZURE_DEVOPS_TOKEN` | Services bearer token or narrowly scoped personal access token |
| Model-provider key | Match the secret name in `.pipr/config.ts` |

Grant read code, contribute to pull requests, manage pull request threads, and create pull request statuses.

## Use a branch-policy pipeline

Use the generated pipeline only when the executed YAML is immutable to pull requests. Azure build validation can execute proposed pipeline content, so an untrusted contributor could replace the review step and read credentials before Pipr starts.

Add the model key as a secret variable and use the generated pipeline as branch-policy build validation. Azure DevOps Services can use `ubuntu-latest`; Server requires a self-hosted agent with Docker and trust for the Server certificate.

The pipeline receives Azure's `SYSTEM_*` and `BUILD_*` variables automatically. It still requires full git history so Pipr can load base-branch config and construct the diff.

## Configure a trusted service-hook worker

Run one worker for one checkout:

```bash
export AZURE_DEVOPS_ORGANIZATION="example"
export AZURE_DEVOPS_PROJECT="project"
export AZURE_DEVOPS_BEARER_TOKEN="..."
export PIPR_AZURE_SUBSCRIPTION_ID="..."
export PIPR_WEBHOOK_SECRET="..."
export DEEPSEEK_API_KEY="..."

pipr webhook serve \
  --host azure-devops \
  --repository repository \
  --workspace /srv/pipr/repository \
  --database /var/lib/pipr/webhooks.sqlite \
  --hostname 127.0.0.1 \
  --port 8787
```

For Azure DevOps Server, use `AZURE_DEVOPS_COLLECTION_URL`, `AZURE_DEVOPS_API_VERSION`, and `AZURE_DEVOPS_TOKEN`.

Prefer an Entra service principal or managed identity for Services. A personal access token used for full command support needs `Code (Read & write)`, `Code (Status)`, `Identity (Read)`, and `Security (Manage)`. If commands are disabled, omit the identity and security scopes.

Create service-hook subscriptions for:

- `git.pullrequest.created`
- `git.pullrequest.updated` with resource version `1.0`
- `ms.vss-code.git-pullrequest-comment-event`

Authenticate each hook with HTTP Basic auth whose password is `PIPR_WEBHOOK_SECRET`, or use an HTTPS proxy that adds `X-Pipr-Webhook-Secret`. Set `PIPR_AZURE_SUBSCRIPTION_ID` to the subscription ID and run a separate worker for each subscription.

Use [Deploy the webhook runner with Docker](/docs/guide/webhook-docker) for persistent state, certificates, and health checks.

## Supported behavior

Services and supported Server releases provide:

- pull request creation and update reviews
- trusted config and exact-head checkout
- main comments and left-side or right-side multiline findings
- `@pipr` commands with effective repository permission checks
- verifier replies and thread resolution
- task and aggregate pull request statuses
- stale-head rejection before publication

Azure DevOps does not expose a stable native suggested-change format, so Pipr renders replacement code in fenced blocks.
