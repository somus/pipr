Use a custom task when `pipr.review(...)` cannot express the required orchestration. A task gathers context, runs typed agents, and emits one final result.

## Build a custom review

A custom workflow combines a model, agent, and task with its triggers:

```ts twoslash
import { definePipr } from "@usepipr/sdk";
import type { DiffContext } from "@usepipr/sdk";

export default definePipr((pipr) => {
  const model = pipr.model("deepseek/deepseek-v4-pro");

  const securityAgent = pipr.agent({
    name: "security",
    model,
    instructions: "Report exploitable security risks introduced by the change.",
    output: pipr.schemas.review,
    prompt: (_input: { diff: DiffContext }) => "Review this change for security risks.",
  });

  pipr.task({
    name: "security-review",
    on: { changeRequest: ["opened", "updated"] },
    check: { name: "security review", required: true },
    async run(ctx) {
      const diff = await ctx.change.diff({
        compressed: true,
        paths: { include: ["src/**"] },
      });
      const result = await ctx.pi.run(securityAgent, { diff });
      const { findings } = ctx.review.select(result.inlineFindings);

      await ctx.comment({
        main: result.summary.body,
        inlineFindings: findings,
      });
    },
  });
});
```

Pass the `ctx.change.diff()` value in the agent input. Pipr detects it and adds the changed-code context and any bounded read tools needed for a reduced manifest.

## Use task context

Task handlers receive provider-neutral context:

| API | Purpose |
| --- | --- |
| `ctx.change.diff(options)` | Build changed-code context and valid inline ranges. |
| `ctx.change.changedFiles()` | Inspect changed file paths without running a model. |
| `ctx.pi.run(agent, input, options)` | Run a typed agent. |
| `ctx.pi.all(requests)` | Run independent agents concurrently. |
| `ctx.review.select(findings, options?)` | Validate, deduplicate, rank, and cap findings before task code consumes them. |
| `ctx.review.prior()` | Read prior Pipr-owned findings for the task. |
| `ctx.comment(value)` | Emit final review output. |
| `ctx.command?.reply(markdown)` | Emit a command response. |
| `ctx.check.gate(findings, options)` | Derive the task check from blocking findings. |
| `ctx.check.pass/fail/neutral(summary?)` | Set one task check outcome. |
| `ctx.log` | Write runtime diagnostics. |

A task must emit exactly one final result. Agent output remains task-local until the task calls `ctx.comment(...)` or `ctx.command.reply(...)`.

## Select findings before task decisions

Call `ctx.review.select(...)` before findings affect a required check, table, or second-stage agent:

```ts twoslash
// @include: task-result
const paths = { include: ["src/**"] };
const { findings, dropped } = ctx.review.select(result.inlineFindings, {
  paths,
  limit: result.inlineFindings.length,
});

ctx.check.gate(findings, { failOn: () => true });

await ctx.comment({
  main: dropped.length > 0 ? `Review complete. ${dropped.length} findings dropped.` : "Review complete.",
  inlineFindings: findings,
});
```

Pipr validates against the full runtime Diff Manifest and current event head. It preserves extra fields such as severity on returned findings and reports each dropped finding with its reason. If you map or combine an agent's finding arrays, pass `paths` explicitly; Pipr can infer the scope only from the exact arrays returned by `ctx.pi.run(...)`.

`select` caps at `publication.maxInlineComments` by default. Pass `limit` when every valid finding should count toward a check.

## Define custom findings

Use a built-in schema when the agent can return normal review output:

```ts twoslash
// @include: pipr-model
const reviewer = pipr.agent({
  name: "reviewer",
  model,
  instructions: "Report concrete correctness defects.",
  output: pipr.schemas.review,
  prompt: () => "Review the current change request.",
});
```

Use `pipr.finding(...)` to add fields to the core finding contract. Enum fields rank findings in declaration order and can drive `ctx.check.gate(...)`:

```ts twoslash
// @include: pipr-z-builder
const risk = pipr.finding({
  title: z.string(),
  severity: z.enum(["high", "medium", "low"]),
});

const riskOutput = pipr.schema({
  id: "review/risks",
  schema: z.strictObject({ risks: z.array(risk) }),
});
```

Pass the same schema to `ctx.review.select(result.risks, { finding: risk })` so selection ranks by its facets. Keep `suggestedFix` to exact replacement code.

## Read prior state

Use prior state when a rerun needs earlier open findings:

```ts twoslash
// @include: task-pi-review
const prior = await ctx.review.prior();
const result = await ctx.pi.run(reviewer, { diff, prior });
```

Pipr handles main-comment updates, duplicate suppression, and bounded finding storage. Custom tasks only need prior data when it affects their own agent input or output.

## Add checks

Checks publish provider-native task status separately from the review comment:

```ts twoslash
// @include: pipr-builder
pipr.task({
  name: "quality-gate",
  on: { changeRequest: true },
  check: { name: "pipr quality gate", required: true },
  async run(ctx) {
    ctx.check.pass("No blocking findings.");
    await ctx.comment("Quality gate passed.");
  },
});
```

Use checks for merge policy and comments for reviewer-facing detail.

## Accept command input

Command patterns can parse typed arguments:

```ts twoslash
// @include: pipr-ci-agent
pipr.task<{ log: string }>({
  name: "ci-triage",
  on: {
    command: {
      pattern: "@pipr ci <log...>",
      permission: "write",
      parse: ({ log }) => ({ log: log ?? "" }),
    },
  },
  async run(ctx, input) {
    const answer = await ctx.pi.run(ciAgent, { log: input.log });
    await ctx.command?.reply(answer.body);
  },
});
```

## Design rules

- Keep task code deterministic around selection, scope, and output mapping.
- Let agents analyze code; let Pipr validate and publish findings.
- Use `pipr.review(...)` until custom orchestration has a concrete benefit.
- Keep provider-specific payloads and direct comment API calls out of task code.

See the [SDK reference](/docs/reference/sdk-reference#task-context) for complete types.
