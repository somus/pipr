Use a custom task when `pipr.review(...)` cannot express the required orchestration. A task gathers context, runs typed agents, and emits one final result.

## Build a custom review

A custom workflow combines a model, agent, task, and entrypoint:

```ts twoslash
import { definePipr } from "@usepipr/sdk";

export default definePipr((pipr) => {
  const model = pipr.model({
    provider: "deepseek",
    model: "deepseek-v4-pro",
    apiKey: pipr.secret({ name: "DEEPSEEK_API_KEY" }),
  });

  const securityAgent = pipr.agent({
    name: "security",
    model,
    instructions: "Report exploitable security risks introduced by the change.",
    output: pipr.schemas.review,
    prompt: (input: { manifest: unknown }) =>
      pipr.prompt`${pipr.section("Diff Manifest", pipr.json(input.manifest))}`,
  });

  const task = pipr.task({
    name: "security-review",
    check: { name: "security review", required: true },
    async run(ctx) {
      const manifest = await ctx.change.diffManifest({
        compressed: true,
        paths: { include: ["src/**"] },
      });
      const result = await ctx.pi.run(securityAgent, { manifest });

      await ctx.comment({
        main: result.summary.body,
        inlineFindings: result.inlineFindings,
      });
    },
  });

  pipr.on.changeRequest({
    actions: ["opened", "updated"],
    task,
  });
});
```

Pass the Diff Manifest through the `manifest` input field. Pipr adds the changed-code context and any bounded read tools needed for a reduced manifest.

## Use task context

Task handlers receive provider-neutral context:

| API | Purpose |
| --- | --- |
| `ctx.change.diffManifest(options)` | Build changed-code context and valid inline ranges. |
| `ctx.change.changedFiles()` | Inspect changed file paths without running a model. |
| `ctx.pi.run(agent, input, options)` | Run a typed agent. |
| `ctx.review.validateFindings(findings, options?)` | Validate findings before task code consumes them. |
| `ctx.review.prior()` | Read prior Pipr-owned findings for the task. |
| `ctx.comment(value)` | Emit final review output. |
| `ctx.command?.reply(markdown)` | Emit a command response. |
| `ctx.check.pass/fail/neutral(summary?)` | Set one task check outcome. |
| `ctx.log` | Write runtime diagnostics. |

A task must emit exactly one final result. Agent output remains task-local until the task calls `ctx.comment(...)` or `ctx.command.reply(...)`.

## Validate findings before task decisions

Call `ctx.review.validateFindings(...)` before findings affect a required check, table, or second-stage agent:

```ts twoslash
// @include: task-result
const paths = { include: ["src/**"] };
const { validFindings } = ctx.review.validateFindings(result.inlineFindings, {
  paths,
});

if (validFindings.length > 0) {
  ctx.check.fail(`${validFindings.length} blocking findings.`);
} else {
  ctx.check.pass("No blocking findings.");
}

await ctx.comment({
  main: "Review complete.",
  inlineFindings: validFindings,
});
```

Pipr validates against the full runtime Diff Manifest and current event head. It preserves extra fields such as severity on returned findings and records dropped findings in validation metadata. If you map or sort an agent's finding array, pass `paths` explicitly; Pipr can infer the scope only from the exact array returned by `ctx.pi.run(...)`.

Tasks that only forward review output to `ctx.comment(...)` can rely on final publication validation. The final boundary still validates findings when a task uses this operation earlier.

## Define custom output

Use a built-in schema when the agent can return normal review output:

```ts twoslash
// @include: pipr-model
const reviewer = pipr.agent({
  name: "reviewer",
  model,
  instructions: "Report concrete correctness defects.",
  output: pipr.schemas.review,
  prompt: () => "Review the current change request.",
});
```

Use SDK-owned Zod for intermediate data:

```ts twoslash
// @include: pipr-z-builder
const riskOutput = pipr.schema({
  id: "review/risk",
  schema: z.strictObject({
    risk: z.enum(["low", "medium", "high"]),
    reasons: z.array(z.string()),
  }),
});
```

Map custom output into `ReviewFinding[]` before publication. Every inline finding must use a valid path, side, `rangeId`, and line span from the task's manifest. Keep `suggestedFix` to exact replacement code.

## Read prior state

Use prior state when a rerun needs earlier open findings:

```ts twoslash
// @include: task-pi-review
const prior = await ctx.review.prior();
const result = await ctx.pi.run(reviewer, { manifest, prior });
```

Pipr handles main-comment updates, duplicate suppression, and bounded finding storage. Custom tasks only need prior data when it affects their own agent input or output.

## Add checks

Checks publish provider-native task status separately from the review comment:

```ts twoslash
// @include: pipr-builder
const task = pipr.task({
  name: "quality-gate",
  check: { name: "pipr quality gate", required: true },
  async run(ctx) {
    ctx.check.pass("No blocking findings.");
    await ctx.comment("Quality gate passed.");
  },
});
```

Use checks for merge policy and comments for reviewer-facing detail.

## Accept command input

Command patterns can parse typed arguments:

```ts twoslash
// @include: pipr-ci-agent
const triage = pipr.task<{ log: string }>({
  name: "ci-triage",
  async run(ctx, input) {
    const answer = await ctx.pi.run(ciAgent, { log: input.log });
    await ctx.command?.reply(answer.body);
  },
});

pipr.command({
  pattern: "@pipr ci <log...>",
  permission: "write",
  parse: ({ log }) => ({ log }),
  task: triage,
});
```

## Design rules

- Keep task code deterministic around selection, scope, and output mapping.
- Let agents analyze code; let Pipr validate and publish findings.
- Use `pipr.review(...)` until custom orchestration has a concrete benefit.
- Keep provider-specific payloads and direct comment API calls out of task code.

See the [SDK reference](/docs/reference/sdk-reference#task-context) for complete types.
