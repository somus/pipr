This tutorial installs Pipr, generates a GitHub workflow and TypeScript config, and publishes a first review. For another code host, use the [provider guides](/docs/guide#start-with-your-code-host).

## Prerequisites

You need a GitHub repository with Actions enabled, permission to add workflows and secrets, and an API key for a model in [Pi's Model Catalog](https://pi.dev/models).

## 1. Install Pipr

Install the latest release and confirm the CLI is available:

```bash
curl -fsSL https://pipr.run/install.sh | sh
pipr --version
```

The installer writes to `~/.local/bin` by default. To pin a release or choose another directory:

```bash
curl -fsSL https://pipr.run/install.sh | PIPR_VERSION=v0.8.0 PIPR_INSTALL_DIR=/usr/local/bin sh # x-release-please-version
```

See the [CLI reference](/docs/reference/cli#pipr-update) for updates and package-manager installation.

## 2. Generate the repository config

From the repository root, generate and validate the default setup:

```bash
pipr init
pipr check
```

`pipr init` creates the review policy under `.pipr/` and the delivery workflow at `.github/workflows/pipr.yml`. Commit the generated `.pipr/bun.lock`; Pipr leaves existing files unchanged unless you pass `--force`.

Use `pipr init --help` for recipes, other code hosts, a custom config directory, or the single-file `--minimal` layout.

## 3. Add the model secret

The default config uses this model profile:

```ts twoslash
// @include: pipr-builder
const model = pipr.model({
  provider: "deepseek",
  model: "deepseek-v4-pro",
  apiKey: pipr.secret({ name: "DEEPSEEK_API_KEY" }),
});
```

Add the matching Actions secret:

```bash
gh secret set DEEPSEEK_API_KEY
```

If you change the provider or secret name in `.pipr/config.ts`, make the workflow expose the same environment variable. Hosted runs read model and publication policy from the base branch, so a pull request cannot replace the policy used to review itself.

## 4. Commit and open a pull request

Commit the generated files:

```bash
git add .pipr .github/workflows/pipr.yml
git commit -m "Add Pipr review"
```

Open or update a pull request. The generated workflow uses a full checkout and grants the permissions needed to publish review comments. Review [GitHub Action permissions](/docs/guide/github-action#permissions) before enabling checks or native thread resolution.

## 5. Verify the review

A successful run can publish:

- one main review comment
- validated inline findings, capped by `.pipr/config.ts`
- check runs when the config enables them

The default config also accepts a new pull request comment containing:

```text
@pipr review
```

Command access defaults to repository `write` permission.

## Troubleshoot the first run

Start with the check that matches the failure:

| Symptom | Check |
| --- | --- |
| Config does not load | Run `pipr check`. |
| The selected plan looks wrong | Run `pipr inspect`. |
| The model does not start | Confirm the secret name and workflow environment mapping. |
| The workflow cannot build the diff | Confirm `actions/checkout` uses `fetch-depth: 0`. |
| The workflow runs but publishes nothing | Check workflow permissions and the run result. |
| Inline findings are missing | Inspect `droppedFindings` in the result. |

See [Troubleshooting](/docs/guide/troubleshooting) for detailed diagnostics.
